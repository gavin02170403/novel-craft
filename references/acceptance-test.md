# Acceptance Test · v1.0

> 基于"调色师"小样书的验收标准。
> 后续修改 Skill 时，用此清单回归测试，防止越改越复杂。

---

## 测试项目

### 1. 路由正确性

| # | 场景 | 预期路由 | 验证方式 |
|---|------|---------|---------|
| 1.1 | 新目录无 state.json | 建议 init | 触发 init 流程 |
| 1.2 | init 完成，无总纲 | 建议 plan（总纲） | 触发 plan 流程 |
| 1.3 | 有章纲，无正文 | 进入 write | 触发 write 流程 |
| 1.4 | 有草稿 | 进入 review | 触发 review 流程 |
| 1.5 | 有 reviewed | 进入 polish | 触发 polish 流程 |
| 1.6 | 当前章 % 10 == 0 | 建议 maintain | 提示维护 |
| 1.7 | 有 overdue 线索 | 警告 + 建议 maintain | 优先处理 |

### 2. 最小读取约束

| # | 阶段 | 最大读取文件数 | 验证方式 |
|---|------|---------------|---------|
| 2.1 | init | 无限制（新建项目） | 确认只生成骨架 |
| 2.2 | plan | ≤4 | state.json + 不可变核心 + 总纲 + 已规划卷 |
| 2.3 | write | ≤5 | state.json + 上一章末尾 + 本章章纲 + 轨道表命中行 + 出场角色语音 |
| 2.4 | review | ≤5 | state.json + 正文 + 章纲 + 上一章末尾 + 出场角色语音 |
| 2.5 | polish | ≤4 | state.json + 正文 + 上一章末尾 + 下一章开头 |
| 2.6 | maintain | ≤4 | state.json + 轨道表 + 检查单回溯 + 事件时间线 |

### 3. 线索轨道表机制

| # | 检查项 | 通过标准 |
|---|--------|---------|
| 3.1 | 写前只读命中行 | 只读 `下次该出现 <= 本章 && active && 紧张度 >=3` |
| 3.2 | 写后更新 | 紧张度/上次出现/最近一次形态/下次该出现 均有更新 |
| 3.3 | 跨章连续性 | 相邻章节的线索推进有逻辑承接，无跳跃 |
| 3.4 | 读者可见度控制 | 关键线索的读者可见度为"隐藏"或"暗示"，不提前剧透 |

### 4. 检查单回溯机制

| # | 检查项 | 通过标准 |
|-------|--------|---------|
| 4.1 | 四章分类 | 每章必须分类为累加/清零/转向/冗余之一 |
| 4.2 | 冗余预警 | 连续2章冗余 → 警告；连续3章冗余 → 触发 maintain |
| 4.3 | 被动主角预警 | 连续2章主角无主动选择 → 下一章必须安排主动决策 |
| 4.4 | 审查记录 | review 后必须写入检查单，含"必须改/建议改/可保留/写入台账"四块 |

### 5. 修改不覆盖原则

| # | 检查项 | 通过标准 |
|---|--------|---------|
| 5.1 | review 不覆盖原文 | 必须改 → 生成 `.polished.md` 副本 |
| 5.2 | polish 不覆盖原文 | 默认在副本上修改，用户确认后才覆盖 |
| 5.3 | 章节状态分离 | `chapter_status` 与 `review_result` 独立存储 |

### 6. 状态源优先级

| # | 冲突场景 | 主状态源 |
|---|---------|---------|
| 6.1 | 章节状态冲突 | `state.json` 的 `chapter_status` |
| 6.2 | 线索紧张度冲突 | `线索轨道表.md` |
| 6.3 | 剧情事实冲突 | `检查单回溯.md` + 正文 |
| 6.4 | 设定冲突 | `不可变核心.md` |
| 6.5 | 自动覆盖 | **不允许**——发现冲突先提示用户 |

### 7. 去AI味四规则

| # | 规则 | 通过标准 |
|---|------|---------|
| 7.1 | 破折号限额 | 全文破折号 ≤ 原文的 20% |
| 7.2 | 动作链条压缩 | 无"首先…然后…接着…最后"式拆解 |
| 7.3 | 感官留白 | 同一段落 ≤ 2 种感官 |
| 7.4 | 斩断空镜余音 | 结尾不停在fade-out式虚写 |
| 7.5 | 衔接检查 | 动机/线索/情绪三问至少回答两个 |

### 8. 性能指标（真实项目观察）

| 指标 | 目标 | 观察方式 |
|------|------|---------|
| 写前准备时间 | ≤ 5 分钟 | 计时：读上一章 + 扫轨道表 |
| 写后登记时间 | ≤ 2 分钟 | 计时：检查单4问 + 更新轨道表 |
| 线索维护频率 | 每10章一次 | 检查 maintain 触发记录 |
| 审查具体问题数 | ≥ 3 条/章 | 检查审查报告，避免形式化打勾 |
| 状态机漂移率 | 0 | 检查 state.json 与实际文件是否一致 |

## 回归测试脚本（手动）

修改 Skill 后，按以下步骤验证：

1. 新建一个空目录，触发 init → 确认骨架正确生成
2. 说"写第1章" → 确认路由到 plan（无章纲时先规划）
3. 生成3章章纲后说"写第1章" → 确认只读取5个文件
4. 写完3章后说"审第3章" → 确认输出"必须改/建议改/可保留/写入台账"四块
5. 检查 state.json → 确认 `chapter_status` 与 `review_result` 分离
6. 说"维护" → 确认触发 maintain，输出维护报告
7. 检查 `线索轨道表.md` → 确认紧张度更新正确
8. 故意制造冲突（如修改 state.json 的 chapter_status 与正文 frontmatter 不一致）→ 确认 Agent 提示用户，不自动覆盖

全部通过 = v1.0 合格。
